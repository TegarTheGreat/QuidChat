# Website Widget Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One `<script>` tag a business pastes into its website, producing a working chat assistant that answers from that business's own documents and shows where each answer came from.

**Architecture:** New package `packages/widget`. Vanilla TypeScript compiled to a single self-contained IIFE — no framework, no runtime dependency, nothing to install on the host page. It renders inside a shadow root so the host site's CSS cannot break it and its own CSS cannot leak out.

**Tech Stack:** TypeScript, `tsdown` bundling to a single file, `fetch`, Shadow DOM. Tests with vitest against a stubbed `fetch` and a real DOM via `happy-dom`.

## Why this plan exists

The server can answer questions, but only something like `curl` can ask them. This is the first piece a business owner and their customers actually see and touch. Everything before it was necessary; none of it was visible.

## Global Constraints

- Node `>=22.22.3`. TypeScript strict; `exactOptionalPropertyTypes: true`.
- **Everything in professional English**: comments, identifiers, test names, error messages. Only text a visitor reads is configurable per tenant, and its default lives in the database.
- **One new dev dependency is permitted** — `happy-dom`, for DOM tests. No runtime dependencies: the bundle a business embeds must contain nothing but our own code.
- The bundle must be self-contained and must not fetch anything except the QuidChat API.
- Commits carry **no attribution trailer of any kind**. `git add` with explicit paths, never `git add -A`.
- `pnpm build` is part of every task's verification.
- Any claim that a property is pinned must be proved by breaking the code and watching the test fail.

## Decisions worth stating before the tasks

**Shadow DOM, not an iframe.** An iframe would isolate styles too, but it cannot be sized to its content without message passing, it breaks text selection across the boundary, and it makes the widget feel like a foreign object on the page. A shadow root gives style isolation in both directions with none of that. The cost is that the host page's `font-family` will not inherit, so the widget must set its own — deliberately, because inheriting a host site's arbitrary typography is how a widget ends up unreadable.

**Citations are shown, not hidden behind a hover.** The product's entire claim is that answers come from the business's own documents. If a visitor cannot see that, the claim is invisible to the only person it is meant to reassure. Each `business_claim` segment renders with its source document title beside it.

**A refusal renders as a normal message, not an error.** When the assistant has nothing to answer from, it says so. That is the product working correctly. Styling it as a failure would teach visitors that the assistant is broken when it is being honest.

**The script tag carries configuration in `data-` attributes**, so a business can paste one line without writing JavaScript:

```html
<script src="https://cdn.example/quidchat.js"
        data-quidchat-tenant="toko-buku-sejahtera"
        data-quidchat-api="https://chat.example.com"
        defer></script>
```

### Task 1: The bundle, the shadow root, and one round trip

**Files:**
- Create: `packages/widget/package.json`, `packages/widget/tsconfig.json`
- Create: `packages/widget/src/config.ts`
- Create: `packages/widget/src/api.ts`
- Create: `packages/widget/src/ui.ts`
- Create: `packages/widget/src/index.ts`
- Create: `packages/widget/src/config.test.ts`
- Create: `packages/widget/src/api.test.ts`

- [ ] **Step 1: Scaffold**

`package.json` builds a single IIFE:

```json
{
  "name": "@quidchat/widget",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "engines": { "node": ">=22.22.3" },
  "exports": { ".": "./src/index.ts" },
  "scripts": {
    "build": "tsdown src/index.ts --format iife --minify",
    "typecheck": "tsc --noEmit"
  },
  "dependencies": {},
  "devDependencies": { "happy-dom": "^20.0.0" }
}
```

`dependencies` is empty and must stay empty. A business pastes this file onto its website; anything we add, their visitors download.

- [ ] **Step 2: Configuration read from the script tag**

`config.ts` exposes `readConfig(script: HTMLScriptElement): WidgetConfig` reading `data-quidchat-tenant` and `data-quidchat-api`.

Rules, each tested:
- A missing tenant attribute is a thrown error naming the attribute. Failing loudly at load beats a widget that renders and silently cannot talk to anything.
- A missing api attribute defaults to the origin the script itself was served from, so the common single-host deployment needs no second attribute.
- A trailing slash on the api value is trimmed, so both forms behave identically.

- [ ] **Step 3: The API client**

`api.ts` exposes `sendMessage(cfg, { conversationId?, message })` calling `POST {api}/v1/chat`.

What it must handle, each tested against a stubbed `fetch`:
- A `200` with `kind: "answered"` returns segments and cited chunk ids.
- A `200` with `kind: "refused"` returns the refusal — **not** thrown. A refusal is a successful outcome and throwing here would push the UI into an error state for correct behaviour.
- `403` produces an error whose message says the site is not authorised for this assistant. That is what a business will see if they have not added their domain to the allowlist, and it is the single most likely setup mistake, so the message must point at the cause rather than saying "forbidden".
- `404` says the tenant key is unknown.
- `503` and any network failure produce a neutral "temporarily unavailable" error — never the server's internal text, which the server already refuses to leak.
- The returned `conversationId` is remembered and sent on the next message, so a follow-up question has context.

- [ ] **Step 4: The UI**

`ui.ts` mounts a shadow root containing a launcher button, a panel with a message list, a text input, and a send button. All CSS lives in one `<style>` inside the shadow root.

Requirements that are easy to skip and expensive to add later:
- **Keyboard**: Enter sends, Shift+Enter inserts a newline, Escape closes the panel. The input receives focus when the panel opens.
- **Accessibility**: the launcher has an `aria-label`, the panel has `role="dialog"` with `aria-modal`, and the message list is an `aria-live="polite"` region so a screen reader announces replies as they arrive.
- **Citations**: each `business_claim` segment shows its source document title. A `general` segment shows none.
- **Pending state**: the send button disables and a typing indicator appears while a request is in flight, so a visitor does not send the same question three times.
- **The visitor's own message appears immediately**, before the reply arrives. Waiting for the server to echo it makes the widget feel broken on a slow connection.

- [ ] **Step 5: Tests**

`config.test.ts` and `api.test.ts` cover Steps 2 and 3 exhaustively. For the UI, test behaviour rather than markup — assert that sending a message appends a visitor bubble, that a refusal renders as a message rather than an error, and that a `business_claim` renders its document title. Do not assert class names or DOM structure; those are implementation and will churn.

- [ ] **Step 6: Verification**

```bash
pnpm install
pnpm test && pnpm typecheck && pnpm lint && pnpm build
```

Then check the bundle is genuinely self-contained: `ls -la packages/widget/dist/` and confirm one file, then `grep -c 'http' packages/widget/dist/*.js` and confirm the only URLs are ones the config builds — no CDN, no font, no analytics.

Then break the refusal path: make `sendMessage` throw on `kind: "refused"`, confirm the refusal test fails, restore.

- [ ] **Step 7: Commit**

```bash
git add packages/widget pnpm-lock.yaml
git commit -m "feat(widget): one script tag, a shadow-rooted assistant"
```

### Task 2: Theme from the tenant, and an embed snippet the panel can show

**Files:**
- Modify: `packages/widget/src/api.ts`, `packages/widget/src/ui.ts`
- Create: `packages/widget/src/theme.ts`, `packages/widget/src/theme.test.ts`
- Modify: `packages/server/src/chat.ts` (a small public config endpoint)

- [ ] **Step 1: A public config endpoint**

`tenant_settings.widget_theme` is a `jsonb` column that nothing reads. Add `GET /v1/widget-config?tenantSlug=…` returning only what a widget needs: the theme, and the greeting to show before the first message.

It is subject to the same origin allowlist as the chat endpoint. And it must return **nothing else** from `tenant_settings` — that table holds the escalation target, the budget, and model names, none of which belong in a public response. Return an explicit allowlist of fields rather than the row minus a few, so a future column is private by default instead of public by accident.

- [ ] **Step 2: Apply the theme safely**

`theme.ts` maps the theme object to CSS custom properties on the shadow root: accent colour, corner radius, position (left or right).

**Every value must be validated before it reaches CSS.** A colour must match a strict pattern; a radius must be a bounded number; a position must be one of two literals. Anything else falls back to the default. Interpolating an unvalidated string into a stylesheet is a CSS injection, and the value here comes from the database, which the admin panel will let a tenant edit — so it is user input, however trusted the path feels.

Tests: each valid value applies; each malformed value falls back rather than being interpolated; an absent theme yields the default.

- [ ] **Step 3: Verification, then break the validator**

Replace the colour validator with a pass-through, confirm the malformed-colour test fails, restore. That test is the one standing between a tenant's theme field and arbitrary CSS on their visitors' pages.

- [ ] **Step 4: Commit**

```bash
git add packages/widget/src packages/server/src
git commit -m "feat(widget): apply the tenant's theme, validating every value"
```

## Definition of Done

- A single `<script>` tag with two `data-` attributes produces a working assistant on any page.
- The bundle has zero runtime dependencies and fetches nothing but the QuidChat API.
- Answers show which document each business claim came from.
- A refusal reads as a message, not an error; a `403` explains that the domain is not on the allowlist.
- Keyboard and screen-reader support work: Enter, Shift+Enter, Escape, focus on open, and a polite live region.
- Theme values from the database are validated before reaching CSS, and the public config endpoint exposes an explicit allowlist of fields.
- `pnpm test`, `pnpm typecheck`, `pnpm lint` (zero warnings) and `pnpm build` all green.
