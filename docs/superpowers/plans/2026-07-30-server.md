# Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Historical record.** This plan describes work that is complete. The code has moved on since
> it was written — most visibly, the codebase was translated to English after these tasks landed,
> so the Indonesian strings in the code samples below are what was built at the time, not what is
> in the repository now. Read it for the reasoning behind a decision; read the code for what the
> code does.


**Goal:** An HTTP server that lets a real visitor on a real website get a grounded, cited answer from a business's own documents — the first point at which QuidChat does anything a user can see.

**Architecture:** New package `packages/server`. Node's built-in `node:http` — no framework, no new runtime dependency. It composes what already exists: `answer()` from `@quidchat/core`, `createStore` from `@quidchat/db`, and a provider from `@quidchat/providers`.

**Tech Stack:** Node 22 `node:http`, `fetch` for nothing (the server receives, it does not call out except through providers).

## Why this plan exists

The pipeline works and is heavily tested, but only against a fake provider and an in-memory database. Nothing can call it. This is the layer that turns a tested library into a product.

It also discharges a debt recorded in spec §11.5: `answer()` deliberately lets store failures propagate, because escalation reasons are a business signal and an unreachable database is not one. That decision assumed a server-side catch-all would exist. This plan builds it.

## Global Constraints

- Node `>=22.22.3`. TypeScript strict; `exactOptionalPropertyTypes: true`.
- ESM only; TypeScript source imports carry the `.js` extension.
- **Code comments and commit messages in English.** Identifiers in English. Only product copy stays Indonesian — the refusal text and system prompt already live in the database and in `packages/core`.
- **No new runtime dependencies.** `node:http` is enough for v1.
- **RLS remains the sole tenant isolation mechanism.** Every query goes through `withTenant`, with exactly one documented exception described in Task 1.
- Every `execute()` result goes through `rowsOf()`.
- Tests must not bind a fixed port and must not reach the network. Start the server on port `0` and read the assigned port.
- Commits carry **no attribution trailer of any kind**. `git add` with explicit paths, never `git add -A`.
- `pnpm build` is part of every task's verification.
- Any claim that a property is pinned must be proved by breaking the code and watching the test fail. Three hardening rounds on this project found fourteen defects that way and none by reading code.

## Two design decisions worth stating before the tasks

**The answer cannot be streamed token by token, and that is not a limitation to work around.** Grounding validation runs on the *complete* answer: a segment claiming a warranty term is only allowed through if it carries a citation that appears in the retrieved candidate set. Streaming raw tokens to the visitor would show text that has not been validated yet, and the whole product promise is that unsourced claims never reach a customer. So SSE carries **progress events** — searching, writing, done — and the answer arrives as one validated payload. Task 3 does this, and the reason belongs in a comment, because "add streaming" is exactly the kind of improvement a future contributor would attempt.

**Resolving a tenant from a public site key requires one query before the tenant is known.** That query cannot go through `withTenant`, because `withTenant` needs the tenant id that the query is looking up. This is the same hazard §11.5 records for `admin_sessions`. It gets exactly one narrow, documented function — not a general-purpose raw handle available to the rest of the server.

- [ ] **Step 2: The one narrow raw-handle query**

Create `packages/server/src/tenant-lookup.ts`:

```ts
import type { QuidDb } from "@quidchat/db"
import { sql } from "drizzle-orm"

function rowsOf(res: unknown): Record<string, unknown>[] {
  return Array.isArray(res)
    ? (res as Record<string, unknown>[])
    : ((res as { rows?: Record<string, unknown>[] }).rows ?? [])
}

export type TenantIdentity = { tenantId: string; allowedOrigins: string[] }

/**
 * Resolves a tenant from its public site slug, and returns the origins that slug is
 * allowed to be embedded on.
 *
 * THIS IS THE ONLY QUERY IN THE SERVER THAT BYPASSES ROW-LEVEL SECURITY, and it has to:
 * `withTenant` needs a tenant id, and this is the lookup that produces one. There is no
 * ordering of operations that avoids it.
 *
 * It is kept deliberately narrow rather than exposing a general raw-handle helper. It
 * takes a slug, returns an id and an origin list, and touches nothing else. Every other
 * query in this package goes through `withTenant`. If a second bypass is ever needed,
 * it belongs beside this one with its own justification, not hidden inside a route.
 *
 * The slug is public by design — it ships inside a website's HTML, exactly like the app
 * id of any hosted chat widget. It is not a secret and must never be treated as one; the
 * origin allowlist is what limits where it can be used.
 */
export async function lookupTenantBySlug(
  db: QuidDb,
  slug: string,
): Promise<TenantIdentity | null> {
  const res = await db.execute(sql`
    SELECT t.id, s.allowed_origins
    FROM tenants t
    JOIN tenant_settings s ON s.tenant_id = t.id
    WHERE t.slug = ${slug}
  `)
  const row = rowsOf(res)[0]
  if (!row) return null
  return {
    tenantId: row.id as string,
    allowedOrigins: (row.allowed_origins ?? []) as string[],
  }
}
```

- [ ] **Step 3: Write the failing test**

Create `packages/server/src/server.test.ts`. It starts the real server on port `0`, uses a real PGlite database through `freshPglite`, and a `FakeProvider` from `@quidchat/core/testing`, so the whole path is exercised without a network or an API key.

Cases that must be covered:

- A seeded tenant with a document containing a warranty term, asked about that term over HTTP, returns `200` with `kind: "answered"` and a non-empty `citedChunkIds`. This is the end-to-end proof that the product works.
- The same request when the knowledge base has nothing relevant returns `200` with `kind: "refused"` and `reason: "no_source"` — a refusal is a successful response, not an error, and the status code must say so.
- An unknown slug returns `404`.
- A request whose `Origin` header is not in `allowed_origins` returns `403`, **even when the slug is valid**. The origin check is what stops another site from mounting a business's assistant.
- An empty `allowed_origins` list means "not yet configured" and returns `403`, not "allow everything". Defaulting an unset allowlist to open would silently expose every freshly created tenant.
- A request with no `Origin` header at all (a curl or a server-side call) returns `403` for the same reason.
- A malformed body returns `400`.
- A `GET` on the chat path returns `405`.
- The conversation is created on first message and reused when the client sends back the `conversationId` it received, proven by asserting the second response carries the same id and that the transcript then holds four messages — two user turns and two assistant turns.

- [ ] **Step 4: Implement the route**

`packages/server/src/chat.ts` holds the handler. Shape of the request:

```ts
type ChatRequest = {
  /** Public site slug, shipped in the page. Not a secret. */
  tenantSlug: string
  /** Absent on the first message of a conversation. */
  conversationId?: string
  message: string
}
```

Order of operations, and each step exists for a reason:

1. Method and content type. Reject anything but `POST` with `405`.
2. Parse and validate the body. A missing or non-string `message`, or a `message` longer than a sane bound, is `400`. Bound the body size while reading it rather than after — an unbounded read is a denial-of-service with no code required.
3. `lookupTenantBySlug`. Unknown slug is `404`.
4. **Origin check**, after the lookup because the allowlist comes from it. The `Origin` header must appear in `allowedOrigins`. Absent header, empty allowlist, or no match is `403`.
5. Create the conversation if `conversationId` is absent, inside `withTenant`.
6. `answer({ store, provider, tenantId, conversationId, history, question })`. History comes from the stored transcript for that conversation, oldest first, so a follow-up question has context.
7. Respond with the `PipelineResult` as JSON.

`packages/server/src/server.ts` wires it with `node:http` and exposes:

```ts
export type ServerDeps = {
  db: QuidDb
  provider: Provider
  /** Called for operational failures. Defaults to `console.error`. Injectable so tests
   *  can assert that a failure was logged rather than swallowed. */
  logError?: (message: string, cause: unknown) => void
}
```

### Task 2: The error boundary, and the budget guard

**Files:**
- Modify: `packages/server/src/server.ts`, `packages/server/src/chat.ts`
- Create: `packages/server/src/budget.ts`
- Modify: `packages/server/src/server.test.ts`

- [ ] **Step 1: The catch-all that §11.5 promised**

`answer()` lets store failures propagate on purpose: escalation reasons are the signal a business owner reads to decide what content to write, and an unreachable database is not that signal. That decision assumed this boundary exists. Build it.

Every route runs inside a handler that catches everything and:

- responds `503` with a JSON body carrying a neutral, visitor-safe message — never an internal error string, which can leak schema names, file paths, or query text;
- calls `logError` so the failure lands in **operational** logs;
- writes **nothing** to the `escalations` table. That is the whole point. Infrastructure noise in that table sends a business owner rewriting a knowledge base that was never the problem.

A test must assert all three: the status, that `logError` was called, and that `escalations` is still empty afterwards. The third assertion is the one that would catch a well-meaning future change that "helpfully" records the outage as an escalation.

- [ ] **Step 2: The budget guard**

`tenant_settings.monthly_budget_cents` exists and nothing reads it. A tenant that has exhausted its budget must be refused **before** any provider call, otherwise the budget is advisory rather than real.

`packages/server/src/budget.ts`:

```ts
/**
 * Sums this calendar month's spend for a tenant. Returns cents.
 *
 * `monthly_budget_cents = 0` means unlimited, not zero — that is the column's default,
 * and treating the default as "spend nothing" would refuse every request on a fresh
 * install. Ugly, but the alternative is a migration to distinguish unset from zero, and
 * this reading is what the admin panel will present.
 */
export async function spentThisMonthCents(db: QuidDb, tenantId: string): Promise<number>
```

Before calling `answer()`, if the budget is non-zero and spend has reached it, record an escalation with reason `budget_exhausted` — which **is** a legitimate business signal, unlike an outage — and return the refusal. Do not call the provider.

Tests: a tenant under budget answers; a tenant at budget is refused with `budget_exhausted` and `provider.calls` is empty; a tenant with budget `0` answers regardless of spend.

- [ ] **Step 3: Record usage so the budget can ever be reached**

`usage_events` exists and nothing writes to it. After a successful answer, write one row with the model, token counts, and cost in cents.

Cost needs a per-model price table. Keep it small, explicit, and honest: a `Record<string, { inputPerMTokenCents: number; outputPerMTokenCents: number }>` with a comment stating that prices change and this table is a starting point the admin panel will make editable. An unknown model records `cost_cents: 0` rather than guessing — a wrong number is worse than a visible zero, because a wrong number silently distorts every budget decision built on it.

### Task 3: Progress events over SSE

**Files:**
- Create: `packages/server/src/events.ts`
- Modify: `packages/server/src/chat.ts`, `packages/server/src/server.test.ts`

- [ ] **Step 1: Add a streaming variant of the chat route**

`POST /v1/chat/stream` behaves exactly like `/v1/chat` but responds with `text/event-stream`, emitting:

```
event: progress
data: {"stage":"retrieving"}

event: progress
data: {"stage":"generating"}

event: result
data: {"kind":"answered","segments":[…],"citedChunkIds":[…]}
```

The comment above it must state plainly **why the answer is not streamed token by token**: grounding validation runs on the complete answer, so streaming raw tokens would put unvalidated claims in front of a customer, which is the exact failure this product is built to prevent. Without that comment, "add token streaming" is the obvious next improvement and it would quietly break the product's central promise.

- [ ] **Step 2: Tests**

- The stream emits at least one `progress` event before the `result` event, proving the client can show activity.
- The `result` payload is byte-identical to what the non-streaming route returns for the same request — otherwise two code paths drift and one of them stops being tested.
- A refusal also arrives as a `result` event, not as an error event. A refusal is a successful outcome.
- The response carries `Content-Type: text/event-stream` and `Cache-Control: no-cache`.

Then break the identical-payload property: change one route to wrap its result in an extra object, confirm the comparison test fails, restore.

## Definition of Done

- A visitor's question over HTTP returns a cited answer drawn from the business's own documents, proven end to end against a real database.
- A refusal is a `200` carrying a reason, not an error.
- An unknown slug is `404`; a disallowed, missing, or unconfigured origin is `403`.
- Any unexpected failure is a `503` with a neutral message, logged operationally, and **absent** from the `escalations` table.
- The spend limit is enforced before the provider is called, and usage is recorded so the limit can be reached.
- Progress is observable while an answer is validated, and the reason tokens are not streamed is written down where someone would otherwise change it.
- `pnpm test`, `pnpm typecheck`, `pnpm lint` (zero warnings) and `pnpm build` all green.
